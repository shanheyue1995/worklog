# 工作快录 — 提示词记录

这份文件记录两件事：

1. 这个项目是怎么一步步"说"出来的——按时间顺序整理用过的提示词，以及每次得到了什么结论。
2. 提示词是怎么写的——可复用的模板，以及这个项目里踩过的坑。

它既是给以后回来继续做的人看的，也是给接手这个仓库的 AI 助手看的。
提示词按当时的意图整理过，去掉了重复和口误，保留了关键约束。

---

## 一、提示词的时间线

### 阶段 1：立项与需求澄清

> 「我想做一个快速记录工作内容的安卓 APP，目标用户是在学校维护电子教学设备的老师，
> 解决打字记录麻烦、不能导出工作记录的痛点，打算先从 MVP 版本开始。
> 你觉得这一版做哪些功能比较合适？先做最基本的功能，其余功能后面再迭代。
> 你觉得前面这些想法有没有什么问题？」

得到的结论：

- 目标用户很明确（一个人群、一个场景），所以 MVP 可以很小。
- 助手反问并确认了几个决定性问题：记录的字段有哪些、照片怎么处理、数据存哪、要不要登录。
- 明确"这一版不做"：不做云同步、不做多人协作、不做统计报表、不做文本输入以外的语音方案。

### 阶段 2：补齐关键约束

> 「1. 导出的记录要带当时的照片。
> 2. 记录应该有这样几个字段：时间（年月日时分）、地点、出现的问题／解决方法。
> 3. 第一版要做成安卓手机里的软件，打开就能用，不用上云，存在本地就行。」

这三句话基本定死了 MVP 的形态：**本地优先、字段极简、照片跟着报告走**。

### 阶段 3：产品细节上的两处修正

> 「长期没导出的提醒你打算怎么做？是否可以参考多邻国——长期不用软件，图标会变色。
> 回到我们这个 APP：长期没有导出，图标根据间隔时间从绿色变黄、橙、红。」
>
> 「导出报告不需要加抬头。」

得到的结论：

- 提醒分三层：桌面小组件（颜色分级）、打开应用时的提示条、每月 1 号的通知。
- 报告只要内容，不要"工作报告"之类的标题栏，直接能打印、能发微信。

### 阶段 4：提醒方案定稿

> 「小组件 + 打开时的提示条，通知按月份走（每月 1 号提醒一次，用户可以点击关闭）。」

### 阶段 5：先写文档，再动手

> 「帮我整理一份产品设计文档吧。不用太详细，把整体方向和主要功能梳理出来就可以。」

产出：[产品设计文档.md](产品设计文档.md)（背景、定位、场景、MVP 范围、界面规范、决策记录）。

### 阶段 6：先看 Demo，再定界面

> 「帮我做一个 Demo，不用实现真实的功能，数据模拟一下就行。我主要想看整体界面和操作流程是否合理。」
>
> 「参考市面上成熟的类似功能软件的 UI 设计，美化页面」
>
> 「我在 project 文件夹下放了一个 design-md 文件夹，里面是各大知名公司网站的设计 design.md，
> 帮我快速浏览一下，选择两到三个和我这个 APP 比较符合的设计，根据它的 design.md 列出几个设计 demo 供我参考。」
>
> 「这是语雀手机 APP 页面截图，参考它帮我设计一个 demo。」

得到的经验：**给参考物（截图、设计稿、design.md）比给形容词有效得多。**
这一轮之后界面定稿为"语雀风格"：单一白卡片 + 细线分隔 + 底部胶囊工具栏 + 克制的绿色。

### 阶段 7：技术选型讨论

> 「1. 报告生成长图。2. APP 内相机连拍不出界面。3. 对 JS 更熟悉，但是能实现功能优先。」
>
> 「1. 报告还是生成 PDF 格式。2. 改用系统相机。3. 就在这台机器上开发。
> 4. 把我上面美化后的 UI 设计记录在设计文档中。5. 按照上面说的，现在请你写一个技术方案文档，放在 docs 文件夹里面。」

得到的结论：

- 报告用 PDF，不用长图（打印和转发都更稳）。
- 拍照改用系统相机，不自己写相机界面（少一个权限、少一堆机型兼容问题）。
- 语言选 Kotlin + Compose，而不是用户更熟的 JS：**能实现功能优先**，安卓原生方案的坑最少。
- 产出：[技术方案文档.md](技术方案文档.md)。

### 阶段 8：定名字、定环境

> 「1. 名称改成'工作快录'，包名就用你推荐的。2. 系统相册不存。3. 确定好了就安装系统环境。」
>
> 「帮我把刚才安装的工具都放在项目文件夹的工具链文件夹中。」
>
> 「帮我把路径中的中文改成英文吧。然后开始下一步。」
>
> 「下面全部交给你完成，直到打包到手机。每一步先自己验证，没错再下一步。」

得到的约定：

- 应用名"工作快录"，包名 `com.worklog.quickrecord`。
- 照片存 App 私有目录，**不进系统相册**（这是老师的真实需求：相册里一堆设备照片很乱）。
- JDK／Gradle／Android SDK 放进工程内的 `toolchain/`，并加进 `.gitignore`。
- 工程路径从中文改成纯英文（中文路径在部分构建工具里会出问题）。
- 每一步自己先验证，再走下一步。

### 阶段 9：真机迭代（大量细节提示词）

这一阶段提示词都是"现象 + 期望"的写法，可以直接抄：

> 「小组件样式太丑，参考其他笔记类型的小组件美化一下。」
>
> 「新建记录中'按住说话，自动转成文字'逻辑错了，google 国内用不了。我建议直接去掉此按钮和功能，
> 因为现在的手机输入法都有语音输入的功能。」
>
> 「记录详情页面中的删除按钮没有边框，设计成和编辑按钮一样的胶囊形状。」
>
> 「'记录详情'页的编辑按钮是灰色的而且没有像删除按钮那样的边框，非常不明显。」
>
> 「所有的'返回'按钮都替换成我给你的返回图标。」
>
> 「在导出记录页增加一个自定义时间范围的功能。」
>
> 「导出记录页面的预览，怎么没有新加的两条记录？是否因为是 BUG 导致预览不更新？」
>
> 「判定用户是否导出文件应该是在用户真实保存下载文件或分享后，
> 而不是用户只点了生成报告在预览的时候就判定已导出。」
>
> 「进入 APP 页面内的左上小图标要换成 small-icon.png 这个 PNG 文件，调整大小使其美观。」

得到的经验：

- 描述界面问题时，说清楚**在哪一页、哪个控件、现在什么样、想要什么样**，一次就能改对。
- 有怀疑是 BUG 的，直接说"我怀疑是 BUG，因为……"，助手会去查根因而不是绕过去。
- 需求变了就说"去掉这个功能"，不要留着半成品——比如语音输入按钮，国内用不了就删掉。

### 阶段 10：准备开源

> 「我想在之后把此项目开源到 GitHub。帮我整理生成此项目的提示词文件，生成一份 readme.md 文件，
> 看看还需要什么帮我补充。」

产出：本文件与 [README.md](../README.md)。

## 二、一直生效的协作约定

写在 [AGENTS.md](../AGENTS.md) 里，每次会话都适用：

> 注意事项
> · 每次改动完成后，都必须创建一个对应的 Git commit，以便后续追踪和回滚。
> · 每次更改后，都必须编写或更新相关测试，并在交付给用户前，确保所有测试和验证全部通过。

这两条看起来啰嗦，但在这个项目里都真正救了场：

- 有一次导出预览的问题，改了两轮才找到根因（报告有 2 页，预览只画了第 1 页），
  因为每一步都有提交，回退和对比很轻松。
- 纯逻辑（日期范围、提醒规则、报告排版、导出判定）都被抽成不依赖 Android 的函数并配上单元测试，
  所以改完不用每次都连手机试。

## 三、可复用的提示词模板

### 1. 加一个新功能

```
我想加一个功能：<一句话说清要它干什么>。
使用场景是：<谁、什么时候、为什么需要>。
约束：<必须/不能做什么，比如"不要新增权限""不要联网""不要动现有数据结构">。
验收标准：<做到什么程度算完成>。
先别写代码，先告诉我你打算怎么做、有没有更简单的方案。
```

### 2. 报一个 Bug

```
<哪一页/哪个操作> 有问题：我做了 <操作步骤>，期望 <应该发生什么>，实际 <发生了什么>。
我怀疑是 <可以写你的猜测，也可以写"不确定">。
顺便确认一下有没有别的入口会被同样的问题影响。
```

### 3. 调整界面

```
参考这张截图/这个设计稿（附上文件）：<要抄的是哪一点：排版、留白、圆角、配色>。
具体位置：<第几页、哪个按钮>。现在的问题：<太丑/太挤/不明显>。
可以顺手做的小调整你看着办，但现有功能一个都不能少。
```

### 4. 让助手自己去真机验证

```
下面交给你完成：改完自己装到手机上验证，截图或日志确认没问题，再告诉我结果。
每一步先自己验证，没错再下一步。
```

### 5. 交接给新会话（或新的贡献者）

```
项目：工作快录，安卓 App，Kotlin + Jetpack Compose + Room，本地存储、无账号无网络。
目录：<项目目录>。设计文档在 docs/ 下，先读 docs/产品设计文档.md 和 docs/技术方案文档.md。
约定：每次改动都要写/更新测试并跑 ./gradlew :app:testDebugUnitTest，全绿后提交一个 commit。
构建与安装：
  ./gradlew :app:assembleDebug
  adb install -r app/build/outputs/apk/debug/app-debug.apk
本次要做的：<任务>。有不确定的地方先问我，不要自己改需求。
```

## 四、这个项目里学到的几条经验

1. **先把"不做"说清楚。** MVP 里写明"不做云同步、不做多人协作"，比列十个想做的功能更有用。
2. **一次只推进一小段，并且每步都能回滚。** 配合"每次改动都提交"，出问题随时退回上一个可用版本。
3. **让机器管规则，让人管判断。** 日期范围、提醒天数、报告排版这类规则交给代码和测试；
   "报告要不要抬头""删不删语音按钮"这类判断由人拍板。
4. **能验证的都要验证。** 真机截图、日志、单元测试都算验证；"应该没问题"不算。
5. **开源前把私人内容拿掉。** 这个仓库的截图里出现过真实的学校设备和同事名字，
   对外发布时要换成假数据截图；提交用的邮箱也建议换成 GitHub 的 noreply 地址。
